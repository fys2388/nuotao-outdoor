# Nuotao AI OS 前端双业务架构 v3.1

文档版本：v3.1  
生效范围：`frontend/` 管理控制台  
产品定位：面向全球市场的 AI 原生 B2C + B2B 跨境电商经营操作系统

## 1. 审计结论

当前前端的主要问题不是视觉细节，而是业务边界和运行契约不清晰：

1. 内部经营控制台与 B2B 客户门户需要独立入口和独立登录态，门户不能复用内部管理端令牌。
2. B2C、B2B、供应链、营销、M5/M6 能力混在同一层菜单，存在重复入口和错误归属。
3. 页面切换使用组件内状态，没有 URL 路由。刷新、收藏、分享和从通知跳转都会丢失上下文。
4. 多个页面在 API 失败后回退到模拟数据，经营者无法判断屏幕上的数字是否真实。
5. 部分按钮只显示成功提示，没有调用后端，例如订单同步、库存调整和物流刷新。
6. B2B 管理接口需要登录态，但控制台没有统一登录和 Token 注入。
7. 商品、客户、订单没有统一携带 `business_model` 上下文，后续容易形成两套重复页面和重复业务逻辑。

## 2. 架构原则

### 2.1 共用底座，业务分流

商品主数据、供应商、采购、库存、物流、AI Agent 和经营分析属于共享底座。B2C 与 B2B 只在销售通道、价格体系、客户类型、订单流程和履约规则上分流。

```text
共享商品/供应链/库存/物流/AI/数据
                    |
          +---------+---------+
          |                   |
        B2C                 B2B
  店铺/零售订单         客户/报价/批发订单
  消费者/售后           代理商/账期/应收
```

### 2.2 前端不是业务规则执行者

前端不得自行决定 `workspace_id`、审批状态、库存扣减结果、退款成功状态、成本可信状态和 Agent 执行权限。所有状态变更必须以后端响应为准。

### 2.3 数据真实性优先

- API 失败时显示错误或“数据不可用”，禁止自动替换成模拟利润、模拟订单或模拟物流轨迹。
- 估算值、已验证值、未配置值和缺少权限必须使用不同标签。
- 没有对应后端能力的页面必须明确显示“尚未接入”，不能展示虚构业务数据。

### 2.4 同一能力只保留一个实现

商品主数据只有一套页面。B2C 商品和 B2B 商品通过业务视角、渠道价格和权限进行筛选，不复制两套 CRUD 页面。订单流程则保留不同状态机和详情视图。

### 4.3 B2B 路由

| 路由 | 页面 | 当前数据状态 |
|---|---|---|
| `/b2b/overview` | B2B 经营 | `/api/v1/admin/b2b/stats` 已支持 |
| `/b2b/partners` | 客户与代理商 | `/api/v1/admin/b2b/agents` 已支持 |
| `/b2b/pricing` | 商品目录与阶梯价 | `/api/v1/admin/b2b/prices` 已支持 |
| `/b2b/orders` | B2B 订单 | `/api/v1/admin/b2b/orders` 已支持 |
| `/b2b/rfqs` | RFQ 询盘 | `/api/v1/admin/b2b/rfqs` 已支持创建、受理、报价和状态流转 |
| `/b2b/quotes` | 报价与合同 | `/api/v1/admin/b2b/quotes`、`/contracts` 已支持版本、审批、双签和转订单 |
| `/b2b/receivables` | B2B 应收账款 | `/api/v1/admin/b2b/invoices`、`/receipts`、`/receivables` 已支持发票、收款、核销、账龄和坏账 |
| `/b2b/agreements` | 年度协议与返利 | `/api/v1/admin/b2b/agreements` 与 `/rebate-accruals` 已支持三口径目标、连续阶梯、审批、终止和结算登记 |
| `/b2b/credit` | 信用风控与保险 | `/api/v1/admin/b2b/credit/*` 已支持政策审批、风险快照、人工冻结/解除、保险保单与索赔；前端不自行评分或覆盖金额 |

尚未接入的 B2B 路由必须显示明确的能力缺口和后端前置条件，不展示演示数据。
RFQ、报价、合同、发票、应收和年度协议工作台只读取真实接口，价格来源、版本、签署人、核销、账龄、返利档位和结算状态均可追溯。
信用风控页只展示后端政策、评分、风险快照、状态事件、保单和索赔事实；人工冻结/解除与索赔决定以后端 RBAC 为准，前端不得计算风险动作或绕过订单准入。
Agent 运行数据通过统一 API 客户端携带登录 Token 请求；前端不得使用裸 `fetch` 拼接未验证路径，也不得通过 `X-Workspace-Id` 选择租户。

B2B 客户门户使用 `/portal/*` 路由和独立令牌 `b2b_portal_token`，只展示当前客户自己的数据。门户可以提交 RFQ、查看已发送报价、接受或拒绝报价、登记客户签署，并在合同生效后幂等转换为订单；报价审批和公司签署仍只在内部管理端完成。


路由冒烟测试登录本地管理控制台后访问 B2B 价格、询盘、报价、订单、协议、应收、信用风控与 Agent 路由，并检查 API `401/403` 与控制台错误。信用风控专项测试在 Google Chrome 中完成政策审批、风险评估、自动暂停、人工解除和保险覆盖展示。

## 6. 后端兼容要求

### 6.1 必须保留的字段

订单、客户、商品和价格模型最终需要支持：

```text
business_model = B2C | B2B | BOTH
order_type = B2C | B2B
customer_type = CONSUMER | RETAILER | WHOLESALER | DISTRIBUTOR | AGENT
price_channel = B2C | B2B
price_tier = RETAIL | WHOLESALE_1 | WHOLESALE_2 | DISTRIBUTOR
```

前端已按 B2C/B2B 分离路由，但后端当前仍需补充统一业务域过滤参数。未完成前，不得通过前端拼接多个接口后宣称数据已经归因到对应业务模式。

### 6.2 RFQ 到回款的最小闭环

```text
RFQ
  -> 报价
  -> 客户接受
  -> PO / B2B 订单
  -> 库存预占或采购
  -> 出库与国际物流
  -> 发票与账期
  -> 收款核销
```

已新增 `b2b_rfqs`、`b2b_quotes`、`b2b_contracts`、`b2b_invoices`、`b2b_receipts` 和 `b2b_receivable_entries`，并让 B2B 订单关联 `quote_id` 与 `contract_id`。

### 第一阶段：可运行基础

1. 统一 URL 路由和菜单配置。

4. 建立 B2C 与 B2B 经营视图。
5. 补齐 Loading、Empty、Error、Not Configured 和 Unauthorized 状态。

### 第二阶段：真实业务闭环

1. 商品、订单、客户携带业务模式筛选。
2. B2B 阶梯价与 MOQ 贯穿商品目录和下单校验。**价格簿、版本、审批与阶梯价已完成（`0036`）。**

4. 售后和退款接入统一审批与审计。

### 第三阶段：RFQ 与应收

1. RFQ、报价、合同、PO 全链路。**已完成（`0037`）。**
2. 账期、发票、应收、收款核销和逾期预警。**已完成（`0038`）。**
3. Agent `business_scope`、工具白名单、预算和审批边界。**已完成（`0040`）：Agent 任务和执行可显示、筛选 B2C/B2B/共享范围，后端三层校验工具、预算和审批。**
4. B2B Sales Agent、Quotation Agent、Collection Agent。**已完成首期建议闭环，入口为 `/b2b/ai`，所有结果只供人工审批和执行。**

### 第四阶段：B2B 客户门户

1. 独立 `/portal/login` 与 `/portal/*` 客户工作台。**P2 已完成首期。**
2. 客户自助 RFQ、报价接受/拒绝、合同客户签署和订单转换。**P2 已完成首期。**
3. 工作区、代理商和客户账户三层数据隔离。**P2 已完成首期。**

### 第五阶段：代理商协议与返利

1. 年度/自定义周期协议、目标进度与连续阶梯返利。**P2 已完成首期（`0043`）。**
2. 返利计算、提交、职责分离审批、终止和结算凭证登记。**P2 已完成首期。**
3. `/b2b/agreements` 已完成 Chrome 桌面端真实业务链路验收，并纳入 B2B 路由冒烟回归。

### 第六阶段：信用风控与保险

1. 信用政策、风险快照、自动暂停/冻结和人工解除。**P2 已完成首期（`0044`）。**
2. 保险保单、覆盖展示和索赔状态机。**P2 已完成首期（`0044`），不自动提高额度、投保或确认赔付。**
3. `/b2b/credit` 已完成 Chrome 端到端验收，并纳入 B2B 路由冒烟回归。

### 第七阶段：客户身份与隐私合规

1. 跨渠道身份链接、确定性冲突和管理员审批合并。**P2 已完成首期（`0045`）。**
2. 追加式同意账本、EDM 发送门禁和数据主体请求台账。**P2 已完成首期。**
3. `/settings/customer-data` 已完成 Chrome 桌面端与 390px 移动端验收；前端只展示后端事实，不自行判定身份相同、同意状态或删除结果。

### 第八阶段：多品牌、多法人与内部交易合并

1. 品牌、法人维护和商品品牌绑定使用 `/analytics/consolidation` 与后端真实接口。**P2-7 已完成首期（`0046`）。**
2. 归因支持 B2C 订单、B2B 订单和 B2B 发票；自动推断只使用单品牌、已配置默认法人的完整证据。
3. 内部交易只有管理员批准后才从外部收入中消除；未归因、待审批和缺失成本保持可见。
4. 前端不计算归因结果、消除金额或利润，只提交人工选择并显示后端状态。
5. **P2-8 已完成首期**：商品品牌批量补空、品牌默认法人编辑、归因缺口查询和历史自动补全均使用真实接口，并展示逐项结果。

## 8. 验收标准

- 任何菜单项都有稳定 URL，刷新后仍停留原页面。
- B2C 和 B2B 在导航、业务上下文和权限上明确分流。
- API 失败不展示模拟经营数字，不显示假成功。
- 需要登录的页面在未登录时跳转到 `/login`。
- 所有页面都有加载、空数据、错误、无权限和未配置状态。
- 桌面和移动端均可完成主要导航。
- `npm run build` 通过。
- 核心路由在浏览器中无控制台错误和明显布局重叠。
