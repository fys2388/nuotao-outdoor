## 1. 使用说明

1. 每条决策有唯一编号（DEC-xxx）、日期、分类、决策内容、理由、备选方案、影响与状态。
2. 决策变更时**新增一条记录**（标记状态为「已修订」），不覆盖历史，保证可追溯。
3. 状态定义：`已确认`（决策生效）、`已实施`（已落地）、`已修订`（被新决策替代）、`已废弃`（不再适用）。
4. 本文档与三份规划文档互相引用；冲突时以本文档为准，并同步修订对应文档。

## 3. 详细决策记录

### DEC-001 商业模式：三阶段演进

- **日期**：2026-08-11
- **决策**：按三阶段演进——阶段 1 中国 1688 供应链 + WooCommerce DTC + 中国直发；阶段 2 爆品验证后建海外仓；阶段 3 发展海外代理商与 B2B 渠道。
- **理由**：轻资产起步，用小成本验证单位经济模型；海外仓与 B2B 在数据验证后再投入，避免重资产风险。
- **备选方案**：直接建海外仓起步（风险高）；纯平台铺货（无品牌资产）。
- **影响**：所有系统设计必须支持三阶段平滑演进；订单/库存模型需预留多仓与渠道维度。
- **状态**：已修订（由 DEC-014 替代）

### DEC-002 目标市场

- **日期**：2026-08-11
- **决策**：主市场美国；次市场德国/欧盟；未来扩展英国、加拿大、澳大利亚。
- **理由**：美国户外消费规模大、DTC 接受度高，适合首发验证；德国/欧盟客单价高但合规严格，作为第二增长曲线；英/加/澳同属英语或高购买力市场，可模板化复制。
- **备选方案**：首发英国（物流近但规模小）；首发东南亚（客单价低、毛利承压）。
- **影响**：多币种（USD/EUR，未来 GBP/CAD/AUD）、多语言（英文/德语）、多税制（美国州税、欧盟 IOSS）为系统基线能力；客服覆盖美欧时区。
- **状态**：已确认

### DEC-003 电商平台：WooCommerce

- **日期**：2026-08-11
- **决策**：DTC 独立站采用自托管 WooCommerce（WordPress）。
- **理由**：开源无订阅费、插件生态成熟、REST API 完备；自托管成本可控，符合低成本原则；品牌资产（域名、内容、数据）完全自有。
- **备选方案**：Shopify（月费 + 交易费，数据锁定风险）；Magento（过重，运维成本高）。
- **影响**：AI OS 通过 API/Webhook 集成 WooCommerce，禁止直改其数据库；需维护 WordPress 安全基线（插件最小化、锁版本、依赖审计）。
- **状态**：已确认

### DEC-004 1688 数据策略

- **日期**：2026-08-11
- **决策**：Phase 1 采用**人工录入 + AI 分析**：人工录入/批量导入候选商品与供应商信息，AI 负责结构化、成本测算、趋势评分与选品建议；Phase 2 在合规前提下探索 API/数据集成。
- **理由**：1688 官方开放能力有限且合规边界需谨慎；人工录入保证数据质量与合规，先跑通业务闭环，量上来后再自动化。
- **备选方案**：直接爬取（合规风险高，数据质量不可控）；等待官方 API（不确定性高，阻塞业务）。
- **影响**：M0/M2 需提供选品录入模板与批量导入能力；成本模型与评分逻辑可先行建设；Phase 2 的集成能力保留扩展点。
- **状态**：已确认

### DEC-005 LLM 多供应商策略

- **日期**：2026-08-11
- **决策**：采用多供应商架构：**OpenAI API 为主，DeepSeek API 为备**，通过 LiteLLM Gateway 统一路由、降级与成本统计，**避免厂商锁定**。
- **理由**：OpenAI 能力全面作主力；DeepSeek 成本低作为降级/低成本任务通道；LiteLLM 屏蔽供应商差异，模型可热切换。
- **备选方案**：单一供应商直连（简单但锁定风险、无降级）；自研网关（维护成本高）。
- **影响**：业务代码禁止直连单一模型供应商；所有 LLM 调用走网关；按任务类型路由模型并设配额、缓存、预算上限。
- **状态**：已确认

### DEC-006 架构风格

- **日期**：2026-08-11
- **决策**：Phase 1 采用**模块化单体 + 事件驱动**（Python 服务，PostgreSQL + Redis）；按领域边界组织，预留按域拆分微服务的演进路径。
- **理由**：团队规模小、成本敏感，微服务运维负担重；清晰领域边界可支撑业务增长后的渐进拆分。
- **备选方案**：直接微服务（过度设计，运维成本高）；单文件单体（无法演进）。
- **影响**：领域边界、服务层与数据库 schema 需按拆分目标设计；事件日志（`event_log`）从第一天记录。
- **状态**：已确认

### DEC-007 技术栈基线

- **日期**：2026-08-11
- **决策**：后端 Python 3.12 + FastAPI；AI 编排 LangGraph + LiteLLM；PostgreSQL 16（业务库 + pgvector）；Redis（缓存/队列）；WooCommerce 电商；Docker Compose 部署；GitHub Actions CI/CD；React 管理控制台。
- **理由**：AI 生态最强、开源免费、招人容易；组件数量少、运维简单；满足低成本与可演进要求。
- **备选方案**：Node.js（AI 生态弱）；Java/Go（开发效率低、招人成本高）。
- **影响**：新增依赖需评估许可证与维护状态；重大选型变更需更新本文档。
- **状态**：已确认

### DEC-008 AI 治理原则

- **日期**：2026-08-11
- **决策**：Agent 是「提议者」而非「执行者」；高风险操作（发货、退款、改价、删除）必须人审；每次 Agent 运行全链路审计（`ai_agent_runs`）；Agent 只能调用白名单工具。
- **理由**：早期避免 AI 失控造成资金与口碑损失；审计数据同时是评测与优化的数据资产。
- **备选方案**：全自动执行（效率高但风险不可控，不适用于早期）。
- **影响**：审批队列（`ai_suggestions`）为核心组件；所有 Agent 输出先落库、后执行。
- **状态**：已确认

### DEC-009 成本原则

- **日期**：2026-08-11
- **决策**：开源优先；LLM 与付费 SaaS 设预算上限与降级链（LLM 不可用 → 规则引擎 → 人工）；每 Agent 设月度成本预算。
- **理由**：跨境 DTC 利润薄，成本失控直接侵蚀毛利；降级链保证业务连续性。
- **备选方案**：无成本护栏（不可接受）；全部自建（开发成本高）。
- **影响**：LiteLLM 需成本统计与告警；客服等场景必须保证「回复不了也比乱回复强」。
- **状态**：已确认

### DEC-010 合规基线

- **日期**：2026-08-11
- **决策**：以 GDPR 为数据合规基线；美国市场接入州销售税（经济关联）自动计算；欧盟市场启用 IOSS 通道并完成德国 LUCID（包装法）登记，含电子件时完成 WEEE 登记。
- **理由**：主/次市场合规是上架与运营的前置条件，罚款与清关失败成本远高于合规投入。
- **备选方案**：先不做欧盟合规（可行但放弃次市场，或承担违规风险）。
- **影响**：税务引擎抽象为「税制适配器」；合规登记（IOSS/LUCID/WEEE）排入 M1 交付物。
- **状态**：已确认

### DEC-011 产品战略 v1

- **日期**：2026-08-11
- **决策**：以 docs/product_strategy.md 为 AI Product Agent 产品判断核心规则：首期聚焦露营灯/头灯、炊具/餐具、收纳/防潮三个核心品类（+1 个探索品类）；采用「引流/主力/Hero/高端」四层价格体系；评分模型 v1（6 维加权 + 否决项）；Hero 每品类 1–2 款。
- **理由**：轻小件控制运费占比（中国直发核心约束）；聚焦策略降低运营复杂度；评分模型为 AI 选品提供可解释、可校准的决策基础。
- **备选方案**：全品类铺货（运费与运营成本失控）；大件/服饰首发（退货与物流风险高，推迟到海外仓阶段）。
- **影响**：sourcing_candidates 需落评分字段；成本模型、合规清单、趋势数据为评分模型数据输入；所有数值参数为 v1 假设，首 50–100 SKU 实测校准。
- **状态**：已确认（v1，待校准）

### DEC-012 供应模式分层策略

- **日期**：2026-08-11
- **决策**：供应模式四层递进——1688 现货贴牌（默认入口）→ 改良贴牌 → ODM 合作 → 自有设计（Phase 3）；升级需测试数据达标 + 人工审批。
- **理由**：默认贴牌以最低成本验证市场；改良与 ODM 在验证后建立差异化；自有设计在 Phase 3 形成品牌护城河，避免一开始重资产。
- **备选方案**：全部自有设计（库存与开发风险高，不适用于验证期）；全部纯贴牌（同质化无壁垒）。
- **影响**：供应商分级（S/A/B/C）与样品/抽检机制为硬约束；知识产权筛查为上架前置条件。
- **状态**：已确认
### DEC-013 运营规则层 v1

- **日期**：2026-08-11
- **决策**：以 docs/operating_rules.md 建立企业运营规则层：10 大规则域（产品选择/评分/定价/利润/供应商/SKU 生命周期/库存/广告测试/客服/Agent 权限），规则模型统一（hard/soft/flow + 版本 + 参数 + 审批级别），通过规则引擎接口（check/evaluate/suggest/override）供 AI Agent 调用。
- **理由**：规则集中、版本化、可配置，是「AI 只提议、关键动作人审、全链路可审计」治理原则的落地载体；避免规则散落在提示词与代码中无法治理。
- **备选方案**：规则写死在 Agent 提示词（不可治理、不可审计）；无规则层（AI 行为不可控）。
- **影响**：开发阶段需实现规则注册表与规则引擎（规格见 operating_rules.md §13）；所有阈值/权重为 v1 假设，随数据校准；权限矩阵（AGENT-PERM）为 Agent 工具白名单的依据。
- **状态**：已确认（v1，待校准）

### DEC-014 B2C + B2B 一体化商务架构

- **日期**：2026-09-13
- **决策**：产品定位更新为「面向全球市场的 AI 原生 B2C + B2B 跨境电商经营操作系统」。商品、供应商、采购、库存、WMS、TMS、CRM、Agent 与 BI 采用共享底座；B2C 与 B2B 保留独立客户、价格、订单和结算流程。详细决策见 `docs/business_decisions/ADR/COMMERCE-001.md`，现状审计见 `docs/b2c_b2b_compatibility_audit.md`。
- **理由**：B2B 不再作为纯后置功能，而是从第一天进入数据库、权限和业务模式设计，避免订单、价格、客户与工作区隔离层后续大规模重构。
- **备选方案**：继续先做 B2C、之后再补 B2B（后期重构成本高）；建设两套独立系统（商品、库存和供应链重复）；继续使用文件型 B2B API（无租户隔离和生产可靠性）。
- **影响**：`orders`、`customer_profiles`、`b2b_agents`、B2B 价格与订单模型必须补充业务模式和工作区隔离；新增 RFQ、报价、合同、发票、收款、应收与状态事件；Agent 增加 `business_scope`；旧 `/m5-m6/b2b/*` 与 `/p3/b2b/*` JSON API 进入废弃流程。
- **状态**：已确认

### DEC-015 B2B 信用风控与信用保险

- **日期**：2026-09-13
- **决策**：B2B 信用控制采用版本化政策、可解释风险评分、确定性自动动作和统一订单准入。客户状态固定为 `normal / watch / hold / frozen`，`hold / frozen` 在所有 B2B 下单入口阻断新增订单；人工冻结、解除、保险索赔批准和结算只允许管理员，必须记录原因与操作者。LLM 只能提供解释或建议，不得改变信用状态。信用保险只缓释风险，不自动提高信用额度、投保或确认赔付。详细设计见 `docs/business_decisions/ADR/FINANCE-003.md`。
- **理由**：静态额度比较无法覆盖逾期、账龄、坏账和保险覆盖，也无法解释谁依据哪版规则冻结客户。把规则集中到可审批、可复现、可审计的服务中，可避免内部销售、客户门户和 Agent 产生不一致结论。
- **备选方案**：继续在各下单服务中比较额度（规则漂移，无法审计）；让 LLM 直接决定冻结或解除（不可复现，金融风险不可接受）；保险覆盖自动增加授信（会把风险缓释误当成真实偿付能力）。
- **影响**：新增信用政策、风险快照、状态事件、保险保单和索赔模型；B2B 报价转订单和门户下单必须调用同一信用服务；外部征信、自动投保和自动索赔属于后续独立决策。
- **状态**：已实施首期（迁移 `0044`，API/RBAC、订单入口、迁移和 Chrome 端到端回归通过）

### DEC-016 跨渠道客户身份、同意与数据主体权利

- **日期**：2026-09-13
- **决策**：以 `customer_accounts` 为统一客户入口；渠道身份只保存工作区级 HMAC-SHA256 指纹，不保存原始邮箱、电话、税号或外部客户 ID。相同身份落到不同账户时只产生确定性冲突和管理员审批合并，禁止模糊或 LLM 自动合并。同意采用追加式账本，撤回事件立即成为 EDM 营销门禁的权威依据；访问、导出、删除、更正和限制处理进入统一数据主体请求台账。删除时匿名化直接身份和非必要行为数据，保留依法需要的订单、合同、发票和账务事实。详细设计见 `docs/business_decisions/ADR/PRIVACY-001.md`，实现说明见 `docs/customer_identity_privacy_design.md`。
- **理由**：B2C、B2B 门户、客服和 CRM 必须回答“同一个人是谁、同意了什么、删除执行到哪一步”。把身份、同意和隐私请求集中在服务层与审计账本中，可避免各渠道各自实现，降低错并客户、营销违规和无法证明履约的风险。
- **备选方案**：按明文邮箱直接合并（泄露和彩虹表风险高）；按姓名/地址模糊自动合并（错并不可逆）；各渠道独立客户 ID（无法形成统一 CRM）；只删除单条行为记录（无法完成身份解绑、同意撤回和财务保留边界）。
- **影响**：生产环境必须配置独立 `CUSTOMER_IDENTITY_HMAC_KEY`；`0045` 新增身份链接、合并、同意、数据主体请求和动作日志；EDM 发送统一检查同意服务；管理端新增 `/settings/customer-data`；删除和限制处理只允许管理员执行并全程审计。后续 B2B 联系人字段级加密、密钥托管和法务保留自动到期仍独立演进。
- **状态**：已实施首期（迁移 `0045`，单测/API RBAC、PostgreSQL 升降级、Chrome 桌面和 390px 验收通过；生产删除开放前仍需 staging、密钥与法务门禁）

### DEC-017 多品牌、多法人与内部交易合并口径

- **日期**：2026-09-13
- **决策**：以 `brands`、`legal_entities`、`products.brand_id` 和 `commerce_attributions` 建立经营管理会计首期合并底座。B2C 订单、B2B 订单和 B2B 发票支持自动或人工归因；自动归因只在商品品牌唯一且品牌存在默认法人时执行。内部交易必须由管理员审批后才能从外部收入中扣除，金额不得超过来源总额，发票应收只在对应发票归因批准后扣减。未归因数据必须显式展示，禁止按名称猜测、按收入比例分摊或伪造完整归因。详细设计见 `docs/multi_brand_legal_entity_consolidation_design.md`。
- **理由**：B2C 与 B2B 共用商品、库存和供应链，但收入可能分属不同品牌与法人。没有交易级归因和内部交易消除，多品牌报表会把内部销售重复计算，也无法解释利润归属。把消除限制为管理员审批，可以在业务可用性和会计准确性之间建立清晰边界。
- **备选方案**：所有维度写死在商品表（订单历史随后续修改漂移）；按商品名称自动匹配品牌（错误率高且不可审计）；把所有收入直接相加（内部交易重复计算）；首期模拟内部利润抵销（缺少买方侧分录，结果不可验证）。
- **影响**：`0046` 新增品牌、法人和归因表并给商品增加品牌外键；B2C 入库、B2B 报价转订单和发票创建自动尝试归因，失败不阻断主业务；管理端新增 `/analytics/consolidation`，写操作按 operator/admin 分权。首期只支持内部收入消除，集团法定合并、内部利润抵销、税务调整和外币折算差额仍属后续范围。
- **状态**：已实施首期（迁移 `0046`，自动归因、审批、报表、RBAC 和 Chrome 端到端回归通过）

### DEC-018 归因主数据治理与批量补全

- **日期**：2026-09-13
- **决策**：商品品牌批量绑定只允许填补 `brand_id IS NULL` 的商品，不覆盖已有品牌；品牌默认法人必须通过明确编辑维护。历史订单和发票只有在商品品牌唯一、品牌存在默认法人，或可继承 B2B 订单完整归因时，才允许自动补全。批量接口逐项返回成功、跳过和失败原因，并为每个实际写入创建审计事件；前端不得把跳过或失败显示为成功。无证据记录继续保留在归因缺口清单，由 operator 人工登记。
- **理由**：批量覆盖商品品牌会改写后续自动归因和报表口径，风险高于单条编辑；静默跳过会让运营误以为数据已修复。把“批量补空”和“人工纠正”分离，可以兼顾效率、可审计性和历史数据安全。
- **备选方案**：批量强制覆盖品牌（可能错误重写主数据）；只提供单条 API（运营效率低）；前端过滤掉不可自动补全记录（隐瞒数据质量）；自动给未知商品分配默认品牌（产生错误报表）。
- **影响**：新增 `/product-brand-gaps`、`/product-brands/bulk`、`/attribution-gaps` 和 `/attribution-gaps/reconcile`；管理端 `/analytics/consolidation` 新增“商品品牌”和“归因缺口”视图，并支持编辑品牌默认法人。成功、跳过、失败逐项展示；已有品牌纠正仍走单条商品品牌接口或后续显式治理流程。
- **状态**：已实施首期（服务/API RBAC、Chrome 完整治理链、390px、类型检查和构建通过）
