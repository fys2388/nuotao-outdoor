# ADR SALES-001 — RFQ、版本化报价与双签合同

> 状态：**Accepted**（2026-09-13）  
> 决策编号：SALES-001  
> 关联：`COMMERCE-001`、`PRICING-001`、`docs/b2c_b2b_compatibility_audit.md`

---

## Context（背景）

B2B 客户成交前通常需要询价、谈判、报价版本、客户审批、合同签署和 PO 转换。如果
直接用 B2B 订单承载这些步骤，会出现订单状态耦合、历史报价被覆盖、审批人与报价
创建人相同、合同签署无法审计，以及重复转换生成多张订单等问题。

因此 RFQ、报价、合同和订单必须使用独立模型与状态机，同时保留完整追溯关系。

## Decision（决策）

### 1. 主链路固定为

```text
RFQ
  -> 报价草稿
  -> 待审批
  -> 已发送
  -> 客户接受
  -> 合同草稿
  -> 双方签署
  -> 合同生效
  -> B2B 订单
```

RFQ、报价、合同和订单不得合并成一张宽表。

### 2. 报价必须版本化并快照价格

- 同一报价号允许多个递增版本。
- 报价行保存 SKU、商品名、数量、单价、价格来源、价格版本和成本快照。
- 已发送、已接受或已转换的报价不得原地修改；调整必须创建新版本。
- 创建报价时只允许解析已发布价格版本。

### 3. 报价审批与发送分离职责

- 报价创建人不能审批自己的报价。
- 过期报价不能发送或接受。
- 只有客户接受的报价才能创建合同。
- 拒绝、过期和取消必须保留原因与事件。

### 4. 合同必须双方签署

- 合同先进入 `pending_signature`。
- 客户和公司分别登记签署人及签署时间。
- 只有双方签署后才自动进入 `active`。
- 单方签署或直接迁移到 `active` 均被拒绝。

### 5. 订单转换具备可追溯与幂等边界

- 只有 `active` 合同对应的 `accepted` 报价可以转换为订单。
- 订单保存 `quote_id`、`contract_id`，订单行保存 `quote_item_id`。
- `(workspace_id, quote_id)` 唯一约束防止重复转换。
- 转换时再次检查客户信用额度，并写入审计事件。

## Consequences（后果）

### 正面

- 每次谈判和报价版本可完整审计。
- 合同签署责任人和时间可追溯。
- 订单价格可以反查到价格版本和报价行。
- 重复转换、越权审批和过期报价无法进入履约。

### 成本

- 销售操作比直接下单增加审批和签署步骤。
- 报价修订必须创建新版本，不能覆盖历史。
- 外部电子签平台接入前，签署登记仍由内部运营确认。

## Verification（验收）

- RFQ 合法状态迁移可用，非法跳转返回冲突错误。
- 报价创建人不能审批自己的报价。
- 过期报价不能发送或接受。
- 只有已接受报价能创建合同。
- 合同双方签署后才生效，重复签署被拒绝。
- 只有生效合同能转订单，重复转换返回同一订单。
- 订单、报价、合同和价格版本三方关系可追溯。
