# ADR FINANCE-003 - 可审计 B2B 信用风控、自动冻结与信用保险

> 状态：**Accepted**（2026-09-13）  
> 决策编号：FINANCE-003  
> 关联：`FINANCE-001`、`SALES-001`、`AGENTS-002`、`COMMERCE-001`

---

## Context（背景）

当前 B2B 信用控制只有一个静态额度比较：

```text
agent.current_balance + new_order_total <= agent.credit_limit
```

该判断分散在报价转订单和门户下单服务中，无法回答：

- 客户当前是正常、观察、暂停还是冻结。
- 逾期金额、逾期天数、额度利用率如何共同形成风险。
- 哪一版规则触发了冻结，是否经过管理员批准。
- 谁能解除冻结，解除原因是什么。
- 信用保险覆盖多少敞口，保单和索赔是否可追溯。
- 为什么一笔订单被阻断，依据是什么。

如果继续把判断散落在各服务中，AI、人工操作和不同销售入口会产生不一致结果，
也无法在资金损失发生后还原决策链。

## Decision（决策）

### 1. 风控规则先审批，再确定性执行

工作区维护版本化 `b2b_credit_policies`。政策包含：

```text
watch_score / hold_score / freeze_score
max_utilization_percent
max_overdue_days
auto_hold_enabled / auto_freeze_enabled
insurance_required_above
```

政策生命周期：

```text
draft -> pending_approval -> active
pending_approval -> rejected -> draft
active -> superseded
```

只有 `active` 政策能用于评分和自动动作。创建人可以提交，管理员负责审批，
提交人不能审批自己的政策。激活新政策时，旧 active 政策自动变为 superseded。

### 2. LLM 不是冻结执行者

Agent 可以解释评分、建议复核或生成催收文案，但：

- 风险分值、风险级别和建议动作由确定性服务计算。
- 自动 hold/freeze 只执行已审批政策中的白名单动作。
- LLM 不得直接修改 `credit_status`，不得解除冻结，不得绕过订单信用校验。
- 任何人工冻结、解除和保险索赔决定均记录操作者、原因和时间。

### 3. 客户信用状态是订单准入唯一事实

`b2b_agents.credit_status`：

```text
normal   正常接单
watch    允许接单，但销售界面提示风险
hold     暂停新增赊销订单，人工复核后可解除
frozen   强制冻结，只有管理员可解除
```

所有 B2B 订单入口必须调用同一信用服务，禁止各自重复比较额度：

- `hold/frozen`：拒绝新增订单。
- `normal/watch`：继续检查订单后总敞口不得超过信用额度。
- `credit_limit = 0`：继续沿用“不启用额度控制”的历史语义。

自动动作产生 `b2b_credit_status_events`，用于完整审计。

### 4. 风险评分必须可解释

首期使用 0-100 分确定性评分：

```text
额度利用率      0-40
逾期敞口占比    0-30
最大逾期天数    0-20
坏账核销占比    0-10
信用保险折扣    0-15
```

落地时总额度利用率、逾期比例、最大逾期天数等上限统一封顶，保险折扣不会让
高风险客户低于 0 分。每次评估保存独立快照和因子明细，不覆盖历史结果。

### 5. 信用保险作为风险缓释，不代替信用额度

新增保单和索赔：

```text
b2b_credit_insurance_policies
b2b_credit_insurance_claims
```

- 保单保存承保人、保单号、覆盖上限、覆盖比例、币种和有效期。
- 有效保险按覆盖比例提供风险折扣，并展示净敞口。
- 首期不因保险自动提高信用额度，不自动提交索赔，不自动确认赔付。
- 索赔必须关联保单和发票，批准、驳回与结算要求管理员和审计记录。

### 6. 评分按需执行，预留调度入口

首期由管理端手动发起单客户评估，也支持列表批量评估。服务函数保持幂等边界：
每次评估产生快照，但自动状态动作只在分数或规则条件变化时生成状态事件。
后续调度器每天批量运行同一服务，不复制规则。

## Consequences（后果）

### 正面

- 所有 B2B 订单入口共享统一信用准入，避免规则漂移。
- 自动冻结可追溯到已批准政策、风险快照和触发因子。
- 人工解除与保险索赔具备职责分离和审计链。
- 信用保险覆盖和风险敞口在经营界面可见。
- 后续 Agent 可以读取同一评分和证据，不自行编造风险结论。

### 成本

- 运营需要维护和审批信用政策。
- 保险覆盖不自动提高额度，仍需人工评估授信。
- 首期不是实时征信系统，不接入外部资信报告；后续接入必须另行设计数据合规。

## Verification（验收）

首期实现与验证完成于 2026-09-13：

- 政策提交人不能审批自己的政策；生效新政策会替代旧 active 政策。
- 评分因子、分值和风险级别可由固定输入复现。
- 满足自动规则时，只有已批准政策允许的动作会改变客户状态。
- `hold/frozen` 客户不能创建或转换 B2B 订单；`watch` 可接单但有明确提示。
- 管理员解除冻结必须填写原因并写入状态事件。
- 保单和索赔按工作区隔离，索赔金额不得超过覆盖和发票余额。
- PostgreSQL `0043 -> 0044 -> 0043 -> 0044` 迁移往返通过。
- 报价转订单与门户下单均调用统一信用服务；`hold / frozen` 返回业务冲突 `409`，超额度订单被拒绝。
- 信用 API 已落实匿名 `401`、角色职责分离、工作区隔离，以及政策审批/人工冻结解除/索赔决定的 admin 权限。
- 管理端 `/b2b/credit` 已接入真实政策、风险快照、状态事件、保险保单和索赔接口。
- Google Chrome 端到端回归完成“政策审批 -> 风险评估 -> 自动暂停 -> 人工解除 -> 保险覆盖展示”，无 API `401/403/500` 和控制台错误。
- 首期实现状态为 **已完成**；外部征信、保险机构 API、自动投保和自动索赔仍不在范围内。
