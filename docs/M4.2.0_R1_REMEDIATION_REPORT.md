# M4.2.0-R1 采购治理整改报告

> 响应 Owner 对 PR #26 的独立审计 REQUEST CHANGES。R1 = Remediation 1。
> 日期：2026-11-21 · 分支：`feat/m4-2-0-procurement-governance`

## 1. 背景与触发

Owner 独立核查 GitHub PR #26（非仅凭 DSH 汇报），在 `d717637` 快照提出关键质疑：

> 审批端点虽有 RBAC，但底层审批 Service 是否能独立证明审批人是「经认证的人类操作者」，而不能只靠传入一个非空 `approved_by` 字符串。

DSH 复核后确认：质疑成立。`d717637` 的 service 层只校验 `approved_by` 非空，鉴权仅存在于 API 层（`require_role`）。任何绕过 API 的调用方（脚本、notebook、未来 agent 路径）都能用一个伪造身份字符串通过审批。

进一步全仓库审计发现两个 Owner 未直接点名、但同样真实的 P0 绕过通道（详见 `M4.2.0_R1_CALLSITE_AUDIT.md`）。本报告记录 R1 全部整改。

## 3. 整改不变量（治理铁律）

M4.2.0 收口确立的单一不变量，R1 使其在**所有入口**成立：

> **采购单到达 `approved` 的唯一路径，是经 RBAC 保护的专用审批端点，且审批 choke point 能独立证明审批人是具备授权角色的认证人类。AI/自动化永不作为自行批准的授权主体。任何非法跳转 fail-closed。**

## 4. 各项整改详情

### R1-1 审批 choke point 强制授权角色（service 层）

`app/services/supply_chain.py::_transition_purchase_order`：

- `target == "approved"` 时，除 `approved_by` 非空外，新增强制 `caller_role ∈ _APPROVAL_ROLES = {admin, operator}`。
- 缺失或角色不足（viewer / customer_service / None）→ 抛 `SupplyChainError`，PO 保持原态（fail-closed）。
- `approve_purchase_order` 透传 `caller_role`；API 端点传入认证主体的 `role`。

**纵深防御**：API 层 `require_role("operator")` + service 层角色校验**双层都必须通过**，任一单独都不足以产生 `approved`。这回应了 Owner 的核心质疑——service 层现在能独立证明审批人授权身份。

### R1-2/R1-3 封堵旧 Fulfillment 入口 + 统一状态机

`app/services/supply_chain.py`：

- 履约尾状态（`shipped`/`delivered`/`completed`）并入 `PO_TRANSITIONS`（`received→shipped→delivered→completed`），消除双状态机。
- 新增统一委托 `transition_purchase_order_status(...)`：
  - 拒绝 `target == "approved"`（引导走专用审批端点）；
  - 校验 `caller_role ∈ {admin, operator}`；
  - 路由到规范转换函数，带操作者身份 + trace_id 落审计事件。

`app/api/v1/endpoints/fulfillment.py::update_po_status`：

- 从「独立状态机 `PO_STATUS_FLOW` + 直改 `po.status` + 无鉴权」改为**代理到 `supply_chain.transition_purchase_order_status`**。
- `approved` → 409；RBAC operator+；身份/角色/trace_id 全留痕。

### R1-4 旧接口 RBAC

`FulfilmentOperator = Annotated[UserResponse, Depends(require_role("operator"))]`：未登录 401、只读/客服 403。

### R1-6 第四套状态机评估

`app/services/purchase_order_service.py`（经 `procurement_workbench.py` 暴露）为**文件存储**，状态集 `pending/confirmed/ordered/...` **不含 `approved`**，最高到 `confirmed`，故无绕过审批面。属既知多状态机技术债（D-2），登记 Backlog，不在本次收口范围。
